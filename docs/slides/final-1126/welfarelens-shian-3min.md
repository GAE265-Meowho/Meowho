# WelfareLens｜世安 3 分鐘專題發表講稿

> 搭配 [個人兩頁 HTML 簡報](./welfarelens-shian-3min.html)，內容同步於團隊 `_src/body.html` 中的「12 安全檢測」及「12b WelfareLens 工程」。發表建議約 **80 秒＋100 秒**；這份文件是口語講稿，不是投影片文字稿。

## 第 1 頁｜從風險到改善證據（約 80 秒）

接著介紹我負責的 WelfareLens，也就是 AI 居家安全檢測。

我們希望解決的是：即使飼主拍下房間，也不一定知道哪些地方對貓咪有潛在風險。因此，同一支居家影片除了建立 3D 房間，也會產生安全檢測報告。

技術上，我們做了三個決策。

第一，不把影片每一格都送進模型。我們透過 FFmpeg 與影像分析選出**最多 8 張代表影格**，降低重複分析。

第二，不把模型說的話直接當成事實。Azure 視覺語言模型輸出結構化資料，程式再用 Schema 驗證、整理重複證據與待確認事項。原始影格還保留時間與 **SHA-256**，用來確認報告引用的圖片能正確對應來源。

第三，除了指出風險，還提供視覺化改善建議。

請看這個**真實報告案例**：影片第 **63.05 秒**，左側牆面有垂落線材。左邊橘色實線框是 AI 估計的危害範圍；右邊綠色虛線框代表改善模擬的場景對位區域。下面則是線材收進理線槽的局部比較。

我們特別標示：**改善後是 AI 模擬，不代表家中真的已經改善。**

## 第 2 頁｜非同步架構與效能最佳化（約 100 秒）

第二個挑戰，是如何讓這套分析穩定整合到網站。

AI 分析需要數分鐘，如果直接在網站請求中同步執行，容易碰到等待與逾時問題。所以我們使用 **PostgreSQL Queue 搭配 Docker Worker**，讓網站先建立工作，再由背景 Worker 自動領件、呼叫 Azure AI，最後產生私有報告。

因為團隊共用資料庫，我們還加入**限定喵戶的領件機制（Scoped Claim）**，搭配鎖定、租約及執行次數，避免錯誤領件，並防止過期結果覆寫新結果。

在效能上，我們發現 AI 改圖會花較多時間。因此，針對**相同六件改圖任務**進行受控測試，從單路改為雙路並行，讓等待模型回應的時間可以重疊。

實測中位數由 **185 秒縮短至 101 秒**，**改圖階段的耗時降低 45.34%**。同時保留至少 12 秒的請求起送間隔，配合共用部署的 6 RPM 限額。

最後，我們在正式網站完成單筆端到端驗收：約 **2.4 秒自動領件**，Worker 約 **4 分 22 秒**完成處理。這次是**本機 Linux AMD64 Docker Worker 串接正式網站與雲端服務**，不是宣稱雲端 Worker 已常駐正式營運。

WelfareLens 的價值，不只是讓 AI 找到潛在風險，而是建立一條**證據可回溯、工作可管理、效能可量測**的實際應用流程。

## 評審可能追問

**為什麼使用 SHA-256？**  
它用來檢查原始影格及報告引用的圖檔內容是否一致；**不能**證明 AI 判斷一定正確。

**為什麼不用同步 API 直接跑？**  
影片分析是分鐘級工作。讓 HTTP 請求快速回應，後續交給背景 Worker，才能管理排隊與失敗狀態。

**為什麼雙路而不是無限增加並行數？**  
因為模型部署有配額限制，增加並行也不等於增加起送速率。受控測試顯示雙路已取得主要效益。

**45.34% 是全部流程加速嗎？**  
不是，**僅限固定六件 Image Edit 的受控實驗**，不是整段影片分析全流程。

**橘框和綠框能代表 AI 精準找到危險物品嗎？**  
橘色實線是 AI 估計的危害位置，綠色虛線用於改善圖的場景對位；兩者都不等於經人工標註驗證的偵測精度。
